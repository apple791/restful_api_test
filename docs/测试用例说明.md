# 酒店预订接口测试用例

预期依据：https://restful-booker.herokuapp.com/apidoc/index.html

| 用例 | 场景 | 关键验证 |
|---|---|---|
| C01 | 已支付定金的预订 | 创建返回 200，提取 bookingid，查询返回的全部字段与提交一致 |
| C02 | 未支付定金的预订 | depositpaid=false 能保存并查询 |
| C03 | 零价格数据 | totalprice=0 原值保存并查询；这是接口数据保真练习，不代表酒店业务允许免费住宿 |
| C04 | 完整业务流程 | 创建、查询、PUT、查询、PATCH、查询、DELETE、查询；删除返回 201，之后查询 404 |
| C05 | 按姓名筛选 | 返回列表包含本次创建的预订 ID，不要求共享服务里只有一条记录 |
| C06-C11 | 缺失或错误 Token，分别执行 PUT、PATCH、DELETE | 响应 403，并再次查询确认预订所有字段保持原样 |
| C12 | 错误账号密码 | HTTP 200、reason=Bad credentials，且不返回 token |
| C13 | 删除后查询 | 仅删除自己的记录，之后查询返回 404 |

所有创建记录的用例均采用唯一姓名隔离数据；fixture 在测试结束后尝试删除本次记录并验证 404。清理失败会记录为 teardown 错误，不伪装成通过。公开共享服务可能被其他使用者重置，需要结合失败证据判断。

另有 11 项离线客户端检查，用于验证请求方法和路径、Token 提取、认证错误、超时后不重复 POST、报告脱敏与会话关闭。这 11 项不计为真实业务覆盖率。
