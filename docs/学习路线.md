# 从已有框架到酒店预订接口测试

本项目是个人学习项目。原来的文章、httpbin、数据库和表单练习保存在 examples 中；新的主线是 Restful-booker 酒店预订接口。

## 建议阅读顺序

1. data/booking_cases.yaml：认识一条预订需要的字段。
2. test_cases/booker/test_create_query.py 中的 test_create_and_read：创建之后查询，核对所有字段。
3. common/booker_client.py：理解业务方法如何调用原来的 send_request。
4. test_cases/booker/conftest.py：理解 fixture 如何获取 Token、准备独立数据并清理。
5. test_booking_lifecycle：理解创建、查询、全量更新、局部更新、删除和再查询。
6. test_unauthorized_write_does_not_change_booking：拒绝请求后仍需核对原数据未被改变。
7. test_cases/unit/test_booker_client.py：理解离线测试与真实接口测试的区别。

## 练习步骤

- 先手动发送一条创建请求，记录请求 JSON、bookingid 和响应内容。
- 再手动查询这个 bookingid，观察为什么不能只检查 HTTP 状态码。
- 单独运行创建查询用例，逐行解释每个断言。
- 修改 YAML 中的价格或是否支付定金，预测结果后执行。
- 故意把某个预期字段写错，观察报告如何展示失败，然后恢复。
- 在测试中途引入断言失败，观察 fixture 仍会执行数据清理。
- 不参考代码，讲清楚 PUT 与 PATCH、Token 的用途和数据隔离的原因。

## 面试表达边界

这是参考已有学习框架、在辅助下改造的个人项目，不是公司生产测试。只有能够独立运行、修改并解释的部分，才应描述为自己的能力。离线用例通过不能等同于真实业务接口通过。不要虚构覆盖率、企业效率提升或线上缺陷数量。

## 可以继续做的扩展

先梳理接口文档对必填字段、字段类型、日期和筛选条件的约定，再补异常及边界用例。不要未经文档依据就假定缺字段一定返回 400。遇到文档与实际不一致时，保留请求、响应、复现步骤与影响说明，不要直接把断言改成当前结果来使测试变绿。

公开 API 没有给你数据库访问权；不要将本地 SQL 数据与其响应对照表述为真实服务落库验证。数据库练习仍可单独保留。
